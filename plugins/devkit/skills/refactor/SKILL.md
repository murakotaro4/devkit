# /refactor - 技術的負債の棚卸し + dig 引き継ぎ

指定範囲を read-only で棚卸しし、優先順位と計画草案を作って dig へ渡す。refactor 自身は実装しない。

## 対象

$ARGUMENTS

## ハーネス・進捗

| 判定 | 質問 |
|---|---|
| `AskUserQuestion` が使える Claude 親 | AskUserQuestion |
| それがなく `spawn_agent` が使える Codex 親 | plan mode は `request_user_input`、通常 mode は選択肢付き自由文 |
| 判定不能 | 選択肢付き自由文 |

`request_user_input` は判定キーにしない。step 1-5 は利用可能なタスクリストまたは通常の進捗報告で開始・完了を示す。委譲・長時間ジョブは個別タスク化し、実体は `git status` / `git diff` で確認して、停滞時だけ状況を報告する。

## read-only 契約

- allowed-tools に Write / Edit を含めず、ファイルの作成・変更・削除、format、lint、test、依存更新、コード生成を行わない。
- Bash は `git log --numstat`、`git ls-files`、`git blame`、`rg` など読み取り用途だけに使う。
- 挙動変更を伴う案は機能変更として分離する。

## フロー

### 1. スコープ確認

調査範囲、目的、後方互換、非対象のうち結果を左右する未知だけ確認する。目的 / 成功条件 / 非対象 / 仮定を短く揃える。

### 2. 棚卸し

各候補に `file:line` 等の根拠、影響、コスト、リスク、区分(リファクタリング / 機能変更 / 要調査)を付ける。

| 観点 | 主な確認 |
|---|---|
| ホットスポット | `git log --numstat` による変更頻度 x サイズ |
| コード重複 | 同型処理、似た分岐、責務の重なり |
| TODO/FIXME | `TODO` / `FIXME` / `XXX` / `HACK` の理由と影響 |
| テスト欠落 | 重要ロジック、回帰、境界条件 |
| 依存 | 未使用、過剰、循環、更新困難な外部結合 |

### 3. 優先順位付け

候補選択の前に第 1 層「推奨候補・判断点サマリー」、後段に第 2 層の根拠詳細を置く。第 1 層は次の 7 カテゴリを持つ。

1. 何を / なぜ
2. 判断してほしい点(推奨付き、最大 3 件程度)
3. 既定からの逸脱・採用した仮定
4. 後戻りしにくい操作・外部影響
5. backend 表(計画レビュー / 実装 / diff レビューはすべて「適用なし」)
6. 検証
7. 独立レビュー状態(`適用なし`、backend も `適用なし`)

一般形の独立レビュー状態は `実施済み(指摘 N 件反映)` / `skip(理由)` / `適用なし`。既定どおりの項目は畳む。

| ランク | 判断基準 |
|---|---|
| S | 高影響、小規模、挙動不変を検証しやすい |
| A | 影響が明確で通常の計画に落とせる |
| B | 事前調査・テスト追加・分割が必要 |
| C | 機能変更、破壊的変更、低い費用対効果など今回扱わない |

影響 x コスト x リスクで格付けし、S/A/B の各候補を名前・ランク・要約付きで個別選択させる。C は報告のみ。要調査はその旨を明記し、選択時は調査先行の草案にする。候補 0 件は質問せず終了、1 件は「引き継ぐ / 見送る」、複数件はハーネスが扱える単位に分ける。選択合計が 0 件なら報告のみで終了する。

### 4. リファクタリング計画

選択候補ごとに、冒頭へ同じ 7 カテゴリを置き、次を含む小さく可逆・挙動不変・検証可能な計画草案を作る。

- 目的と変えないもの
- write_scope
- 実装手順
- 挙動不変の検証
- 完了条件
- 非対象

### 5. dig への引き継ぎで終了

選択済み草案を `dig の step 2` へ渡す。詳細契約は `plugins/devkit/skills/dig/SKILL.md` を参照し、refactor は実装・backend 選択・レビューを行わない。利用可能なら Skill ツールで dig を起動し、それ以外は `$dig` または `/dig` へ渡すよう案内する。ユーザーが望めば計画レポートだけで終了する。

```markdown
## dig step 2 計画草案
## 承認用サマリー
<7 カテゴリ>
## 詳細
### 目的
### write_scope
### 実装手順
### 検証
### 非対象
### refactor 由来の根拠
```

根拠が薄い候補は「要調査」のまま扱い、実装可能と断定しない。
