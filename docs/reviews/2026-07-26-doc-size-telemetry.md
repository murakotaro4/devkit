# 配布ドキュメントのサイズを壁から計測値へ（2026-07-26）

2026-07-25 の圧縮記録が「サイズ上限 4 種」を成果として挙げた判断を覆す一次記録。

## 1. 契機と実測

| 観測 | 数値 |
|---|---:|
| dig SKILL.md | 12,318 / 上限 12,350（余裕 32 字） |
| goal-prompt SKILL.md | 2,077 / 上限 2,080（余裕 3 字） |

安全契約を 1 つ足すたびに判断系の記述を削る交換が発生していた。PR 計画本文と委譲指示に「収まらなければ既存の重複記述を削って収める」という字数交渉が必要になっていた。

## 2. 交換の歪み

2026-07-25 の圧縮で削ったのは例外分岐で、独立レビュー 17 件の大半がそれだった。壁の下では、契約を足すたびに別の契約を削る交換が構造的に起きる。トークン量としては無意味である（dig 12,318 字 ≒ 6k トークン = Opus 5 の 1M context の 0.6%）。

## 3. 何を失うか

壁がなかった頃の dig は 24,064 字だった。壁を外すと同じ膨張が再発しうる。歯止めは独立レビューだけになる。このリスクは面談で明示的に承知したうえで採った。

## 4. 何で代替するか

`cc2cd36`（2026-07-25 の圧縮 + 独立レビュー 10 巡の収束点）を基点とする baseline 比レポートへ置き換える。増加率降順で出し、`CHECKS_FAST` / `CHECKS_FULL` の外に置く。サイズがいくら増えても失敗しない。

基点に圧縮 commit `0b3e7cf` を使わない理由: そこはレビュー収束前の中間状態で、dig 9,964 / repo-loop 7,768 / setup 5,516 と文書の表からも現行上限の由来からも食い違う。`cc2cd36` は 12 ファイルすべてが表と一致する。

## 5. 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 承認前/後で会計を分割 | dig は承認境界でほぼ 50:50 に割れ、前は判断系・後は安全契約という性質差がある。分割しても壁の圧力は残る |
| `references/` への段階的開示 | 未読リスクが新しい失敗モードになる。安全契約が読まれないと事故る |
| 承認を境にスキル 2 分割 | 承認直後に文脈が切れる。保守面積が増える |
| 実行機構の script 化 | 今回の痛みはサイズ上限そのものなので、今回は採らない |
